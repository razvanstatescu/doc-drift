Context

Checkout retries a charge when it does not get an answer within 10 seconds. Before v2, a slow database during peak hours caused duplicate charges: the first request was still running when the retry arrived. In February we refunded 214 duplicates by hand.

Decision

Every POST /v2/charges and POST /v2/refunds must carry an Idempotency-Key header of at least 8 characters. The server stores the key with a hash of the request body and the response it sent:

  • Same key, same body, within 24 hours: return the stored response with idempotent-replay: true. Nothing is created.

  • Same key, different body: 409 idempotency_key_conflict. This is almost always a client bug.

  • No key: 400 idempotency_key_required.

Keys live in the idempotency_keys table in the payments database, written by withIdempotency() in src/idempotency.ts.

sqlTable

Options considered

  1. Keys in Postgres (chosen). Same transaction boundary as the charge, no new dependency.

  2. Keys in Redis. Faster, but a Redis failover could forget a key and allow a duplicate. Duplicates are the exact problem we are solving.

  3. Deduplicate on the PSP side. The PSP supports it, but only per merchant account, and refunds would still be exposed.

Consequences

  • Clients had to start sending keys. We gave them 6 weeks and a 400 with a clear code.

  • A nightly job deletes keys older than 24 hours. The table holds about 2 million rows at peak.
