When to use this runbook

Drain the queue before anything that must not run while settlements are in flight:

  • A database failover that is planned, not forced.

  • A PSP maintenance window announced in advance.

  • A worker release that changes how settlement_jobs rows are claimed.

Draining does not stop charges. POST /v2/charges keeps accepting requests; their settlement jobs are created as held until you resume.

How it works

The API inserts a settlement_jobs row for every charge. Workers claim pending rows in batches with FOR UPDATE SKIP LOCKED. Setting SETTLEMENT_ENQUEUE_PAUSED=true on the API makes new jobs held instead of pending; the workers keep going until no pending row is left.

Steps

  1. Note the current pending count on the Pending settlement jobs panel. Draining takes about 1 minute per 1,000 jobs with 4 workers.

  2. Start the drain from the root of the payments-api repo. The default timeout is 900 seconds.

    bash

    It prints the pending count every 10 seconds and exits 0 when it reaches 0.

  3. If it exits 1 (timeout), the workers are probably failing. Check the worker logs before you retry, and consider scaling up with .

  4. Do the maintenance.

  5. Resume. The script turns enqueue back on and releases every held job to pending. The backlog clears within a few minutes.

drain-queue.sh changes the deployment with kubectl set env. The next Helm release resets it to the chart value, so a deploy during a drain also resumes enqueue. Freeze deploys while draining.
