What it does

When a charge is created, the API writes a row to settlement_jobs and returns at once. The settlement worker picks those rows up and submits the charges to the PSP for capture. The PSP confirms with a charge.settled webhook, which marks the charge settled. The decision to move this out of the request path is .

How work is claimed

Each worker pod runs PAYMENTS_WORKER_CONCURRENCY slots (8 by default). Each slot claims up to SETTLEMENT_BATCH_SIZE rows (50) in one transaction:

SKIP LOCKED means slots and pods never wait on each other, so adding pods adds throughput until the database becomes the limit. When a slot finds nothing to do it sleeps for 2 seconds.

Failure handling

  • If a batch fails, its transaction rolls back and the rows go back to pending for the next claim.

  • If the PSP never sends the webhook, the charge stays in settling. Dead-lettered webhooks are handled in .
