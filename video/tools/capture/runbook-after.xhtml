When to use this runbook

Roll back when a payments-api release is live and at least one of these is true:

  • The charge success rate on the Payments overview dashboard drops below 97% for 5 minutes.

  • p95 latency on POST /v2/charges stays above 800 ms for 5 minutes.

  • Error logs show a spike that started within 30 minutes of the deploy.

If the release also ran a database migration, read Migrations below before step 2. A rollback does not undo schema changes.

Post in the incident channel before you start, and name yourself as the person rolling back. Only one person runs the rollback.

Steps

  1. Confirm the current and previous release. The previous revision is the one you are rolling back to.

    bash

  2. Run the rollback script from the root of the payments-api repo. ROLLBACK_TIMEOUT is in seconds and defaults to 300. Raise it to 600 if the cluster is under load.

    bash

    The script calls helm rollback payments 0 --wait, so it returns only when the previous release is ready or the timeout expires.

  3. Check that the pods are on the previous image tag and passing readiness.

    bash

  4. Watch the charge success rate for 10 minutes. It should be back above 99%.

  5. Freeze deploys: add the deploy-freeze label to the payments-api repo's open release PR and say so in the incident channel.

If the script times out

A timeout usually means the previous image cannot pull or a pod is failing readiness. Do not run the script twice in parallel.

bash

If a pod is stuck, delete it and let the deployment replace it. Then run step 2 again with a longer timeout.

Migrations

Payments migrations are expand-only for 1 release, so the previous release can run against the new schema. If the release notes say the migration was contract (dropped or renamed a column), page the database on-call before rolling back.

After the rollback

  • Open a follow-up in Jira under PAY-6 with the bad release tag and the dashboard screenshot.

  • Keep the freeze until the fix is reviewed by 2 people.
